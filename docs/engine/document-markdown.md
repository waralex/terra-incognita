# Markdown adapter for stable-ID documents

`markdown/document-model.mjs` reuses the existing CommonMark/GFM parser and the
standard mdast Markdown serializer.
The engine stores only blocks; it does not parse Markdown.

## Mapping

- Every import creates an anonymous Section root (title null).
- Top-level headings become nested Sections; title contains inline Markdown.
- Lists become List containers (ordered start and spread preserved).
- List items have their own ID, spread setting and optional Todo/Done checkbox.
- Item text and nested lists are children, in original order.
- Each paragraph gets its own Text block. Code, quotes, tables, HTML,
  definitions and headings inside list items remain textual Markdown blocks.

The importer creates new IDs and commits the complete tree once. It is not an
update/diff importer: importing again must not be presented as retaining old IDs.
`DocumentMarkdown.import` requires author and reason. IDs generated by the parser
are not address paths; moving a section does not rewrite descendants.

## Export semantics

Export produces canonical Markdown, not byte-identical source. Markers, escaping,
line endings and whitespace can normalize. Heading levels derive from Section
nesting; skipped levels are normalized (`# A / ### B` becomes `# A / ## B`).
More than six heading levels is an explicit export error, not silent flattening.

Reference/footnote definitions are supplied as parser context so references can
span Text blocks. That context is not included in the exported content. HTML
remains text and is never executed here. Quotes and their inner structures remain
opaque text. Two adjacent list containers retain distinct list syntax through
the standard serializer's alternating markers.

A section title must serialize as one heading. A checkbox item must begin with a
text paragraph; empty/checkable items with no representable paragraph fail rather
than silently dropping the state. Tight/loose layout is stored in List/ListItem
`spread`, independent of sibling position.

Imports retain the parser's 250000-character limit, at most 1000 blocks and 48
container levels. Export uses one coherent subtree read, at most 10000 nodes;
a depth boundary causes an explicit error rather than a truncated document.
JS rejects positions outside the safe integer range. These are prototype limits,
not promises of arbitrary-size streaming export.

## Local bridge and verification

`crates/terra-core/examples/document-bridge.rs` is a local JSONL process adapter,
not an HTTP server. It owns one dedicated database and supports transact, get,
subtree and history, returning typed error categories. The JS process transport
is in `markdown/document-bridge.mjs`. This bridge is for integration experiments;
request-size checking happens after reading a line, not as a streaming memory cap.

Run:

```sh
RUSTC_WRAPPER= cargo build -p terra-core --example document-bridge
node --test markdown/document-model.test.mjs
node markdown/document-integration.mjs
```

The real-database test imports a document, combines checkbox/reorder/title edits,
checks historical export and stale-edit rejection, moves a section without
rewriting descendants, closes the process and reopens the database. All test data
is in a temporary directory, removed after closing RocksDB.

Document CF codecs are now explicitly versioned (v2); older experimental databases
are rejected instead of silently interpreting a different ListItem encoding. Use a
fresh database when the codec version is incompatible.

Current project memory uses this adapter. No automatic database migration or Markdown text-diff synchronization is provided. See [MCP and service](document-mcp.md).

## Parsed insertions and replacements

`DocumentMarkdown.write(markdown, {author, reason, target, expected})` replaces
one Text leaf with parsed Markdown. Alternatively pass `placement` instead of
`target`/`expected` to insert a fragment. Both use the import parser: each paragraph
is a separate Text, lists have structured items, and headings create sections.
Code, quotes and tables remain individual opaque Text blocks.

Replacement preserves the target ID for the first resulting block; subsequent
blocks have fresh IDs. The old target version and the new blocks are associated
through one transaction, with one reason. There is no separate provenance edge
or arbitrary block matching. Ordinary single-paragraph edits preserve identity.
Neighbors retain their identity and contents (position rebalance can update their
versions). Expected target revision is checked again by the engine at commit.

Container replacement is rejected: this API never implicitly deletes a subtree.
Empty Markdown is rejected; deletion is a separate explicit operation. Invalid
placement/topology rejects the entire transaction. Raw engine Put remains a
low-level full-state API and does not parse Markdown.

When placement targets an existing List (directly or through an item anchor), a
single Markdown list fragment of matching ordered/unordered type contributes its
items to that container. Existing numbering remains authoritative. A list inserted
inside a ListItem remains a nested list; mixed top-level fragments are rejected
when inserting into a List.
